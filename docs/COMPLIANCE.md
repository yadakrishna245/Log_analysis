## Executive Summary

LogSherlock Pro is a **100% on-premises** log analysis application with **zero external network dependencies**. It processes customer log data entirely within the HPE corporate network, on infrastructure fully controlled by HPE IT. This document provides the compliance justification required for deployment approval.

**Key Facts:**
- ✅ No data leaves the corporate network — ever
- ✅ No external API calls, cloud services, or third-party integrations
- ✅ No internet connection required for operation
- ✅ All processing happens on a single server you control
- ✅ Full audit trail of all user actions
- ✅ Standard authentication and access control

## 2. Network Isolation Proof

### Zero External Connections

LogSherlock Pro makes **no outbound network connections** of any kind. This is verifiable by:

#### Code-Level Proof

The application's `requirements.txt` includes no packages that phone home. Analysis of all source code confirms:
- No HTTP client calls to external URLs
- No DNS lookups to external domains
- No socket connections to external IPs
- No SDK integrations with cloud providers
- No telemetry, crash reporting, or usage analytics

#### Network-Level Verification

Administrators can verify with:

```bash
# Monitor all outbound connections from the application
ss -tulnp | grep python

# Should show ONLY:
# tcp  LISTEN  0.0.0.0:8000  (application port)
# tcp  LISTEN  127.0.0.1:5432  (PostgreSQL, if used)

# Verify no DNS queries to external domains
tcpdump -i any port 53 and host <server-ip>
# Should show ZERO results during normal operation

# Firewall verification — block ALL outbound and confirm app still works
iptables -A OUTPUT -m owner --uid-owner logsherlock -j DROP
# Application continues to function normally
```

#### Runtime Verification Script

```bash
#!/bin/bash
# compliance_check.sh — Run periodically to verify no external connections

echo "=== LogSherlock Pro Network Compliance Check ==="
echo "Date: $(date)"
echo ""

# Check listening ports
echo "Listening ports (should be internal only):"
ss -tulnp | grep -E "python|gunicorn|waitress"
echo ""

# Check established connections
echo "Established connections (should be local only):"
ss -tnp | grep -E "python|gunicorn" | grep -v "127.0.0.1"
echo ""

# Check for any external DNS queries in last hour
echo "External DNS queries (should be NONE):"
journalctl -u logsherlock --since "1 hour ago" | grep -i "dns\|resolve\|lookup"
echo ""

echo "=== Check Complete ==="
```

## 3. No External Dependencies at Runtime

### Build-Time vs Runtime Dependencies

| Phase | External Access | Description |
|-------|----------------|-------------|
| **Installation** (one-time) | Yes — pip install | Downloads Python packages from PyPI |
| **Runtime** (ongoing) | **NO** | Zero external connections |

After initial `pip install`, the application is fully self-contained. For air-gapped environments:

```bash
# Download packages on a connected machine
pip download -r requirements.txt -d ./packages/

# Transfer to air-gapped server
scp -r ./packages/ target-server:/opt/logsherlock/

# Install from local packages
pip install --no-index --find-links=/opt/logsherlock/packages -r requirements.txt
```

### No AI/ML Cloud Services

LogSherlock Pro uses **no external AI or ML services**:
- No OpenAI, no Azure AI, no AWS Bedrock
- No cloud-based NLP or text analysis
- Pattern matching is pure regex/keyword — runs locally
- Similarity search uses local algorithms (rapidfuzz, Whoosh)

## 4. Audit Trail

### What Is Logged

| Event | Data Captured |
|-------|--------------|
| User login/logout | Username, timestamp, IP address |
| Ticket creation | User, timestamp, ticket details |
| File upload | User, timestamp, filename, SHA-256 hash, size |
| Analysis execution | User, timestamp, ticket ID, duration |
| Report generation | User, timestamp, ticket ID, format |
| KB article changes | User, timestamp, article ID, action |
| Finding acknowledgment | User, timestamp, finding ID |
| User management | Admin user, timestamp, target user, action |

### Log Format

```
2026-07-15 10:30:45 | INFO     | routes.tickets | User john.doe created ticket #1234
2026-07-15 10:31:02 | INFO     | routes.logs    | User john.doe uploaded customer_logs.7z (245MB, sha256:a1b2c3...)
2026-07-15 10:31:45 | INFO     | engine.analyzer| Analysis complete for ticket #1234: 12 findings in 43s
2026-07-15 10:32:10 | INFO     | routes.reports | User john.doe generated RCA report for ticket #1234
```

### Log Retention

- Application logs: Rotated at 50MB, 10 backup files kept (configurable)
- Audit events: Retained in database indefinitely (or per policy)
- Access logs (nginx): Standard rotation via logrotate

### Audit Access

Logs are stored locally at `/opt/logsherlock/app/logs/` and accessible only to:
- The `logsherlock` service account (write)
- System administrators (read)
- Not accessible via the web interface

## 5. Data Retention

### Configurable Retention Policies

| Data Type | Default Retention | Configurable |
|-----------|-------------------|-------------|
| Tickets | Indefinite | Yes — manual or scheduled deletion |
| Uploaded log files | Indefinite | Yes — auto-purge after N days |
| Analysis findings | Indefinite (with ticket) | Yes — deleted with ticket |
| Reports | Indefinite | Yes — manual cleanup |
| Application logs | 500MB rolling | Yes — via LOG_MAX_SIZE_MB |
| User sessions | 8 hours | Yes — via SESSION_LIFETIME_HOURS |

### Data Deletion

When a ticket is deleted, ALL associated data is removed:
- Ticket metadata (database)
- Uploaded files (filesystem)
- Extracted files (filesystem)
- Analysis findings (database)
- Generated reports (filesystem)

This is enforced by SQLAlchemy cascade deletes and filesystem cleanup.

### Implementing Auto-Purge

```bash
# Cron job to delete tickets older than 90 days
# Add to /etc/cron.d/logsherlock-retention

0 3 * * * logsherlock cd /opt/logsherlock/app && \
    venv/bin/python -c "
from app import create_app
from models import db, Ticket
from datetime import datetime, timedelta

app = create_app()
with app.app_context():
    cutoff = datetime.utcnow() - timedelta(days=90)
    old_tickets = Ticket.query.filter(Ticket.created_at < cutoff, Ticket.status == 'closed').all()
    for t in old_tickets:
        db.session.delete(t)
    db.session.commit()
    print(f'Purged {len(old_tickets)} tickets older than 90 days')
"
```

## 6. Access Control

### Authentication

| Mechanism | Implementation |
|-----------|---------------|
| Password storage | bcrypt with automatic salt (cost factor 12) |
| Session management | Server-side sessions, 8-hour lifetime |
| API authentication | JWT tokens, 24-hour expiration |
| Password requirements | Configurable (minimum length, complexity) |
| Failed login protection | Logged for security monitoring |

### Authorization (Role-Based)

| Role | Create Tickets | Run Analysis | Manage KB | Manage Users | System Config |
|------|:-:|:-:|:-:|:-:|:-:|
| **Viewer** | ❌ | ❌ | ❌ | ❌ | ❌ |
| **Analyst** | ✅ | ✅ | ✅ | ❌ | ❌ |
| **Admin** | ✅ | ✅ | ✅ | ✅ | ✅ |

### Session Security

- Secure cookies (HTTPS-only in production)
- CSRF protection on all state-changing requests
- Automatic session expiration after inactivity
- No "remember me" for sensitive environments

## 7. Comparison with Cloud Alternatives

### Why On-Premises is Safer for Customer Log Data

| Criterion | LogSherlock Pro (On-Prem) | Cloud Solutions (Splunk/Datadog/ELK Cloud) |
|-----------|--------------------------|-------------------------------------------|
| **Data location** | Your server, your rack | Vendor's cloud (US/EU regions) |
| **Data transit** | Never leaves LAN | Crosses internet to vendor |
| **Vendor access** | None | Vendor employees may access |
| **Compliance** | Meets all internal policies by default | Requires vendor security assessment |
| **Data breach risk** | Limited to internal network | Exposed to internet-facing infrastructure |
| **Regulatory** | No cross-border data transfer | May violate data residency requirements |
| **Vendor lock-in** | None — standard Python/PostgreSQL | Proprietary formats and APIs |
| **Cost** | $0 ongoing | $10K-100K+/month for enterprise |
| **Approval process** | Minimal — internal tool on internal infra | Extensive — vendor risk assessment, legal review, DPA |
| **Internet dependency** | None | Complete — no internet = no service |
| **Multi-tenancy risk** | None — single-tenant by design | Shared infrastructure with other customers |

### Specific Risk Comparison

| Risk | On-Prem Mitigation | Cloud Risk |
|------|-------------------|------------|
| Customer data exposure | Data never leaves controlled environment | Data transits internet, stored on shared infra |
| Supply chain attack | Pinned dependencies, no runtime external calls | Vendor's entire dependency chain is attack surface |
| Insider threat (vendor) | N/A — no vendor access | Vendor employees with system access |
| Service outage | Your infrastructure, your control | Vendor outage = total loss of service |
| Price increase | $0 — you own the software | Vendor can increase prices at renewal |
| Feature removal | You control all features | Vendor can deprecate features |
| Data portability | Standard DB, standard files | Proprietary formats require migration effort |
